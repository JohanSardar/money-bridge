# Existing agent finance layers: fork, compose, or build?

**Research cutoff: 2026-10-17.** For Money Bridge's implementation decision. This extends [DECISIONS.md](../design/DECISIONS.md), [existing-tools.md §3](existing-tools.md#3-existing-mcp-servers-and-agent-tools), and [provider-routes.md §10](provider-routes.md#10-open-source-multi-institution-readact-projects-and-health). Their budgeting-app comparisons and provider endpoint inventories are not repeated here.

**Verdict: build a new MIT Money Bridge service, reusing existing MIT adapters and official action clients. Do not fork any of the three original candidates wholesale.** A stronger newly discovered candidate, **Breadbox**, already implements much of the multi-provider, self-hosted read infrastructure. It deserves a serious comparison before implementation, but its AGPL-3.0 license prevents treating a derivative fork as the agreed MIT product. If that license decision changes, **extending Breadbox is the best fork option found**. A separately deployed Breadbox read service is also an integration option; it does not by itself supply Money Bridge's action, approval, event, or permanent-history guarantees.

**No complete substitute was verified.** This is a bounded search result, not proof that none exists. Existing pieces are substantial: normalized bank-data stores, provider adapters, agent interfaces, and individual official action rails. The unfilled combination is a permanent local record across providers plus an enforced action/approval boundary, per-agent authorization, and a replayable financial event feed.

## Evidence and scoring

All URLs were checked or source files retrieved on **2026-10-17**, unless explicitly marked inaccessible. Dates beside commits are upstream committer dates; dates beside announcements are publisher dates. Undated vendor documentation is dated by this retrieval statement. **Source-verified** means inspected public source or first-party documentation, not a working integration. **Unverified** means absent, conflicting, inaccessible, or untested evidence. Product claims are attributed to the vendor. No signup, credential use, bank connection, dependency installation, test execution, or execution of cloned project code occurred. Public repositories were read under `/tmp/finance-oss-review/`.

Fit percentages are **rough analyst judgments, approximately ±10 percentage points**, not measurements, completion estimates, or compatibility probabilities. Weighting: deployment/local ownership 25; normalized multi-provider data/history 25; CLI+MCP+HTTP 15; synchronization/freshness/events 15; official actions with owner approval 10; per-agent authorization/audit 10. Partial capabilities earn partial credit. License and official-API-only requirements remain hard adoption constraints regardless of score. “Write” to a local ledger earns no money-movement credit. An MCP SSE transport earns no financial-event-feed credit.

## 1. Deep source review: the three initial candidates

### 1.1 elcukro/bank-mcp

**Version reviewed:** `c6abad503b1ecec47e80108ef8d0c614da0f4de5`, v0.2.1, committer date **2026-02-23**. [Exact tree](https://github.com/elcukro/bank-mcp/tree/c6abad503b1ecec47e80108ef8d0c614da0f4de5), [commit history](https://github.com/elcukro/bank-mcp/commits/main/). The earlier report's May push timestamp is not the date of this default-branch commit; do not use `pushed_at` as code-freshness evidence.

**Architecture and providers.** TypeScript ESM/Node, official MCP SDK, Zod. An abstract `BankProvider` defines configuration validation, account listing, transaction listing, balance retrieval, and setup fields. The registry constructs Plaid, Teller, Enable Banking, Tink, and Mock providers. Mock is not a fifth financial aggregator. Implementations contain actual HTTP mapping/pagination code: Plaid `/transactions/get` offset pagination; Teller `from_id` pagination and `node:https` client certificates; Tink/Enable Banking cursors. This is more than a catalog of planned connectors. Plaid production setup can require an already-obtained access token; the wrapper does not remove provider onboarding. [Provider contract](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/providers/base.ts), [registry](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/providers/registry.ts), [Teller adapter](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/providers/teller/index.ts), [Plaid setup](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/init/flows/plaid.ts).

**Data/store/freshness.** `BankAccount` is essentially provider UID, IBAN, name, currency, connection ID. `Transaction` has ID, account, date, JavaScript-number amount, currency, description, merchant/category, debit/credit, optional raw data. Balance is amount/currency/type. There is no first-class pending-to-posted relation, observation history, holdings/security/lot, liability detail, document model, or identity reconciliation across providers. Transactions normalize to negative expenses. Only an **in-memory TTL cache** exists: accounts one hour, transactions 15 minutes, balances five minutes. These are cache ages, not upstream freshness guarantees. Queries call upstream; there is no persistent ingestion scheduler or webhook receiver. Restart loses cached financial data. [Types](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/types.ts), [cache](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/utils/cache.ts).

**Actions/auth.** Five read tools over stdio. CLI commands help initialize/connect/refresh provider configuration; this is not a general financial-data CLI+HTTP API. Provider credentials are in owner-only `~/.bank-mcp/config.json` and key files; `0600` protects a file from other ordinary OS users, not from an agent running as the owner. No per-agent keys, resource scopes, action approval, or durable access audit was found. [MCP implementation](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/server.ts), [configuration](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/config.ts).

**Tests/quality/health.** Provider fixtures, paging/mapping and tool tests exist; CI declares build/tests on Ubuntu with three Node versions. These are source-inspected checks, not test results from this research. The separation between provider mapping and tools is easy to understand. Limitations include binary floating-point money, raw upstream error bodies exposed through generic tool errors, and a server-reported version still `0.1.3` while package version is `0.2.1`. Human commit attribution is concentrated in `elcukro`/`maestro`; no broad maintenance organization was established. Cross-OS client examples are not proof of Windows runtime compatibility. [Tests](https://github.com/elcukro/bank-mcp/tree/c6abad503b1ecec47e80108ef8d0c614da0f4de5/tests), [CI](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/.github/workflows/ci.yml), [HTTP errors](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/src/utils/http.ts), [MIT license](https://github.com/elcukro/bank-mcp/blob/c6abad503b1ecec47e80108ef8d0c614da0f4de5/LICENSE).

**Reuse decision.** Good MIT donor for four provider adapters, mTLS setup and fixture examples. A fork would retain little besides those adapters once the cache and query-on-demand design are replaced. Prefer selectively extracting/adapting them with notices, then validating current provider contracts. It is not a near-finished Money Bridge backend.

### 1.2 tomfunk/fungible

**Version reviewed:** `20a7322bf426c284a4b94b75c2b9e8c5bb5ad975`, committer date **2026-10-10**. [Exact tree](https://github.com/tomfunk/fungible/tree/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975), [history](https://github.com/tomfunk/fungible/commits/main/). Recent default-branch commits remove stale code and plaintext-token passthrough, and update encrypted test fixtures. This is actual maintenance evidence, stronger than stars or a README badge.

**Architecture.** TypeScript, Node ≥22, libSQL client against a local SQLite file, Plaid SDK, shared `core/`, Ink/React TUI and Electron GUI. `core/tools.ts` backs the in-app agent, MCP and HTTP API. MCP supports stdio and Streamable HTTP; the HTTP API exposes `POST /tools/:name`, rather than a conventional resource REST API. The Bash `bin/fungible` launcher dispatches MCP/API/export/TUI. Desktop packaging targets macOS/Windows/Linux, but the shell launcher and headless installation need separate Windows validation. [Package manifest](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/package.json), [HTTP API](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/api/server.ts), [MCP](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/mcp/create-server.ts), [launcher](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/bin/fungible).

**Providers/data.** Plaid plus CSV/manual records; no Teller/SimpleFIN/Link/Schwab/Alpaca implementation found in the inspected tree. Tables cover accounts, transactions, category/name/tag rules, imports, balance history, household/profile and app settings. Transactions include pending state, imported source and dedup metadata, with SQLite `REAL` amounts. Plaid-native IDs underpin accounts/items; there is no general multi-provider account identity layer. The inspected tables omit transaction currency and structured holdings/tax lots. Balance history has one value per account/day, overwritten on same-day refresh. This is a personal-finance app model, not a complete raw financial observation model. [Database/migrations](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/core/db.ts), [CSV/Plaid dedup](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/core/dedup.ts).

**Sync/forever/history.** Real `/transactions/sync` pagination accumulates added/modified/removed entries and saves a cursor, with per-item error handling and a 15-minute debounce. Debounce is not a background refresh schedule. Account and balance fetch uses `/accounts/get`, which Plaid documents as cached; it is not a live balance fetch. Removed transactions are deleted through a cascade helper. Comments explicitly acknowledge that cursor reset cannot recover records Plaid no longer returns and that deliberate deletes have no tombstones. The in-process refresh emitter updates the UI; `/notify` signals a refresh. Neither is an externally consumable, durable financial change feed. No provider webhook receiver was found in this path. [Sync implementation](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/core/sync.ts), [refresh emitter](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/core/refresh.ts), [Plaid balance semantics](https://plaid.com/docs/api/accounts/).

**Actions/auth/security.** Actions edit local records/rules/tags/imports; none move bank money. The in-app chat can ask for write confirmation. MCP and HTTP execute shared tools directly, so that chat confirmation is not an authorization boundary for external agents. One optional `FUNGIBLE_API_KEY` protects HTTP, without per-agent/resource scopes. Loopback is default; MCP refuses nonlocal unauthenticated binding, whereas the REST server only warns and can still start. Host/Origin checks, constant-time bearer comparison and request limits are positive source evidence. Plaid tokens use AES-256-GCM with a local `0600` key file; the database itself and owner-process access are not thereby encrypted/isolated. No durable read/action audit log was found. [HTTP guard](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/core/http-guard.ts), [MCP HTTP](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/mcp/http.ts), [token encryption](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/core/crypto.ts), [in-app agent](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/core/agent.ts).

**Tests/quality/health.** Extensive named tests cover sync, CSV parsing/dedup, import previews, write-gating, HTTP auth/origin/body limits, MCP, TUI and GUI behaviors. CI/typecheck/Playwright definitions exist. They were not executed. Shared core routines, parameterized SQL and regression fixtures are useful. App analysis, categorization, household fields, embedded LLM adapters and presentation concerns are interwoven with the tool surface. The multi-step sync writes are not one append-only observation transaction. Current-state mutations, rather than immutable provider revisions, are the bigger fit problem than code style. [Tests](https://github.com/tomfunk/fungible/tree/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/tests), [CI](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/.github/workflows/ci.yml), [MIT license](https://github.com/tomfunk/fungible/blob/20a7322bf426c284a4b94b75c2b9e8c5bb5ad975/LICENSE).

**Reuse decision.** Best of the three if forced to fork a functioning local app, but not the preferred infrastructure foundation. Selectively reuse CSV/dedup tests, Plaid paging, API hardening and the common-tool-dispatch pattern. A wholesale fork requires removing product features while replacing the schema, credentials policy and sync/event core that would supposedly justify the fork.

### 1.3 geofftang/programmatic-finance-tracker

**Version reviewed:** `72d6aa5ff9059f15bb08dfec65d942fd984ecdf6`, committer date **2026-06-18**. Public history has two commits on that date. [Exact tree](https://github.com/geofftang/programmatic-finance-tracker/tree/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6), [history](https://github.com/geofftang/programmatic-finance-tracker/commits/main/).

**Architecture/providers.** Python 3.11+ scripts, `simplefin==0.2.0`, Beancount 3.2.3, beangulp, Fava and SQLite. Flow: SimpleFIN fetch → dated JSON → Beancount extraction → owner review/append → derived SQLite mirror. CSV backfill includes Chase/Citi/Apple Card/Wells Fargo parsers and a date seam separating backfill from ongoing sync. No native MCP, financial HTTP API, agent CLI protocol, action adapter, or provider plugin service. Fava's UI server is not the requested gateway. [Pinned requirements](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/requirements.txt), [fetcher](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/scripts/fetch-simplefin.py), [backfill importer](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/importers/backfill_importer.py).

**Data/storage/freshness.** Ledger postings use `Decimal`, retain `simplefin_id` metadata and double-entry structure; the SQLite query projection converts amounts to floats. Fetch cadence belongs to cron/launchd, with default 45-day lookback; no push or streaming is implemented. Output is one filename per date, so repeated same-day fetches overwrite that day's JSON. The importer consumes its own fetcher's ISO-date intermediate, not raw protocol Unix timestamps. A plain-text ledger can retain entries indefinitely, but the pipeline does not preserve every version of provider data. [SimpleFIN importer](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/importers/simplefin_importer.py), [mirror](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/scripts/build_sqlite_mirror.py).

**Correctness gaps relevant to reuse.** Exact-ID dedup avoids collapsing genuinely repeated equal charges, a useful improvement over fuzzy-only matching. However, its map is keyed only by `simplefin_id`, without account/provider namespace; SimpleFIN transaction identity is account-scoped. A changed transaction with the same ID is treated as a duplicate, not a new revision. Pending lifecycle/reversal handling is not established. Double-entry balance does not prove ingestion completeness: omitting both legs of a transaction also balances. The mirror test reuses the implementation's account-splitting function, so it is not a wholly independent oracle. These are static-review findings, not reproduced live failures. [Dedup implementation](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/importers/simplefin_importer.py), [mirror test](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/tests/test_mirror.py), [SimpleFIN identity contract](https://www.simplefin.org/protocol.html).

**Auth/tests/license/health.** Secrets are loaded from `.env`; the agent is intended to read a `0444` mirror. The design explicitly distinguishes built controls from a **planned** no-egress agent profile. File permissions do not restrict a same-owner agent able to change permissions. No server auth, scoped agent identity, approval or access audit exists. Sixteen test functions cover schema drift, ID dedup, bank sign conventions, transfer clearing and mirror fidelity using synthetic fixtures. The code is small and inspectable, with useful error handling, but personalized account maps/category rules and manual workflow steps remain. Repo MIT does not erase GPL licensing of Beancount/beangulp dependencies. [Security design](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/docs/DESIGN.md), [tests](https://github.com/geofftang/programmatic-finance-tracker/tree/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/tests), [MIT license](https://github.com/geofftang/programmatic-finance-tracker/blob/72d6aa5ff9059f15bb08dfec65d942fd984ecdf6/LICENSE), [Beancount license](https://github.com/beancount/beancount/blob/master/COPYING), [beangulp license](https://github.com/beancount/beangulp/blob/master/LICENSE).

**Reuse decision.** Reuse MIT importer/test ideas, not the whole program. Beancount is a useful optional export/reconciliation target; it is a poor mandatory source of truth for pending observations, webhook processing and action lifecycles. Retaining it as an external optional tool also keeps the license boundary clearer than importing its GPL internals into the MIT core.

## 2. Strongest new discovery: Breadbox

**Source-reviewed HEAD:** `3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2`, **2026-06-30**. Its description explicitly calls it infrastructure: a normalized store queried by agents/dashboards/scripts without sharing bank credentials. This is much closer to the confirmed brief than a budgeting app. [Pinned README](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/README.md).

Verified in code, not merely roadmap:

- A provider interface with link/exchange, incremental transactions, balances, webhook verification, reauth and revoke; implemented Plaid/Teller/SimpleFIN/CSV adapters. A capability distinguishes polling reconciliation from cursor-based changes. Go `decimal.Decimal` amounts; transaction provider/account IDs, pending counterpart ID, dates/times, currency and raw JSON. [Contract](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/provider/provider.go), [registration](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/app/providers.go).
- Plaid JWT/body-hash webhook verification and Teller HMAC verification, sync scheduler and connection health. SimpleFIN correctly reports webhooks unsupported. [Plaid verification](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/provider/plaid/webhook.go), [Teller verification](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/provider/teller/webhook.go), [SimpleFIN limits](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/provider/simplefin/stubs.go).
- CLI, REST/OpenAPI, stdio/HTTP MCP; API-key/OAuth middleware and read-only/full-access tool filtering. An admin UI can be disabled with a headless build. Postgres persistence and encrypted provider credentials exist. [Routes](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/api/router.go), [auth](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/middleware/apikey.go), [MCP filtering/audit](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/mcp/server.go).

Material gaps that prevent calling this Money Bridge already:

1. **No financial action methods in the provider interface.** Local tags/categories/reports are not payments/trades. No provider-execution approval gate was verified.
2. **No financial SSE/WebSocket feed.** `sync logs --follow` explicitly polls every two seconds because the server does not expose sync SSE/WS. MCP streaming does not supply ordered transaction/balance events with replay cursors. [CLI source](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/cli/sync.go).
3. **Latest raw payload is not permanent observation history.** The provider-payload satellite table has a transaction primary key and `updated_at`, rather than one immutable row per observation/revision. `NUMERIC(12,2)` schema fields also need revision for non-two-decimal currencies and precise investment quantities. Holdings/lots/tax-document models were not established in this review. [Payload migration](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/db/migrations/20260614055107_transaction_provider_payloads.sql), [transaction schema](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/db/migrations/00007_transactions.sql).
4. **Audit is useful but weaker than the desired guarantee.** MCP calls log asynchronously with a timeout; logging failures do not fail the call. Request/response storage is truncated at 32 KiB. Defaults purge MCP call records after 30 days and webhook event records after seven; zero disables cleanup. Webhook records retain a payload hash, not the payload. Coverage of every REST/CLI read and durable pre-execution logging remains unverified. [MCP logging](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/mcp/server.go), [retention settings](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/appconfig/keys.go).
5. **Scopes are coarser than the README can suggest.** General API keys validate `read_only` or `full_access`; workflow-specific tool controls do not establish arbitrary per-agent account/provider/action scopes across all doors. Native release targets inspected were Linux/macOS; Windows via a container is plausible, native Windows support unverified. [Key creation](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/internal/service/apikeys.go), [release workflow](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/.github/workflows/release.yml).

**Quality/health judgment:** real migrations, provider mapping fixtures, headless/lite builds, integration tests and CI make it the strongest inspected read-side foundation. Several architecture docs lag source: one still describes only Plaid, while code registers SimpleFIN/Teller. Prefer source. The latest reviewed commit fixes per-run key visibility, a positive security-maintenance signal that also shows the permission surface is evolving. Neither an independent audit nor current production reliability was verified. [CI](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/.github/workflows/ci.yml), [license](https://github.com/canalesb93/breadbox/blob/3f6c0b23520c0e07dbe9f18247b3e42b5bd93cc2/LICENSE).

**Fork/build-on decision:** direct fork is the shortest plausible route if AGPL is acceptable. Under the binding MIT decision, do not copy its implementation into Money Bridge and relabel it MIT. A separately packaged service accessed through its public API is a possible composition boundary, but the proposed packaging/license obligations have not been legally reviewed. It adds Postgres, household/workflow machinery and another deployment to an intended one-person product, while leaving its most distinctive action/event requirements to us. Therefore it is an optional compatibility backend, not the recommended mandatory core.

Code is **GPL-2.0-only**; beangulp is GPL-2.0. Optional external ledger/export is preferable to making GPL accounting internals the MIT gateway's core. |

**Recommended normalized model is a small Money Bridge contract informed by these sources**, rather than a direct copy of Plaid or the whole FDX/ISO schema. This is design inference:

- Separate `Connection`, provider-observed account identity, and owner-resolved physical `Account`. One bank may appear through several providers; matching must not silently combine unrelated accounts.
- Represent money exactly (decimal string plus currency, or integer plus explicit exponent); use higher precision for securities/FX. Never silently turn unknown balances/invalid amounts into zero. Keep current/available/ledger/limit balance kinds distinct.
- Keep provider observation IDs namespaced by provider, connection and account; maintain immutable observations/revisions and explicit pending→posted/reversed/removed relationships. Preserve raw payload, source timestamp if available, retrieval time and normalization version.
- Keep imported evidence and user annotations separate from provider facts; record linkage/dedup decisions and allow reversal. A transaction removed upstream still needs historical evidence locally.
- Model holdings, securities/lots, liabilities and documents separately. Provider payment intents/orders/approvals/settlements are separate from bank transactions, joined by explicit references and later reconciliation.
- Commit normalized changes and an outgoing event/outbox record together. Publish a replayable cursor-based event feed from that local log; provider webhooks are ingestion signals, not the finished event feed.

## 6. Recommended reuse boundary and decision triggers

1. **Keep the new MIT, one-person, headless product.** Reuse official protocol SDKs and review small MIT provider/import components. Start the provider assessment with Actual Sync Hub's orchestration and bank-mcp's compact adapters; do not import both stacks wholesale. Choose language after comparing these donors with deployment goals, not because a finance app happens to use it.
2. **Own the durable store and event contract.** None of the three initial candidates provides the required immutable provider history or replayable local financial events. These are central product behavior, not peripheral glue that a fork would save.
3. **Reuse official action clients behind the independently researched approval boundary.** Link first where eligible; broker and other official APIs by supported account capability. Money-moving methods stay absent for read-only institutions. Do not expose raw upstream action tools to agents and call their conversational confirmation owner approval.
4. **Keep Breadbox as the strongest alternative, with a concrete trigger.** Reconsider an AGPL fork if MIT changes, or a separate Breadbox backend if adopting Postgres/its operational model is acceptable. First resolve immutable history, fine-grained scopes, REST audit, replayable events, action isolation and Windows operation. Current evidence does not justify a mandatory second service merely to save adapter code that has MIT alternatives.
5. **Hosted alternatives are optional connectors, not a silent change of product.** Synci/BankSync are credible documented ways to reduce consumer aggregator onboarding. They change data-processing/availability dependencies and need explicit compatibility with the existing ownership promise. No signup was needed or performed to reach that conclusion.

The decision is **not “everything must be written from scratch.”** Reuse adapters, SDKs, parsers, decimal libraries, fixtures and existing approval providers. Build the thin but consequential local contract that those pieces do not yet share: permanent provenance, provider capabilities, scoped-agent access, financial events, audited intents and owner-approved execution.

## 7. Explicit unresolved claims

- **Production access:** no individual installation's Plaid/Teller/Link/network eligibility was exercised. Teller availability has conflicting non-authoritative reports; leave it capability-gated pending an authoritative contract/owner-authorized pilot.
- **Quality/security:** no candidate test suite or source was executed. Test counts and CI files establish intended coverage only. No independent security audit was verified for the community projects. Encryption implementations were read, not cryptographically or operationally certified.
- **Health metrics:** public GitHub metadata/release/contributor API calls returned **403 rate limit exceeded**. No fresh star counts, comprehensive contributor totals, support response times or all-branch activity are claimed. Inspected Git histories and exact default-branch commits are the health evidence.
- **Search completeness:** mcp.so was inaccessible; the registry finance search was intentionally bounded. Small README-only candidates and commercial backend implementations remain unverified. A connector repository, listing or pitch does not establish a self-hostable service.
- **Schemas/licenses:** current FDX complete downloadable schema, current governing redistribution terms, and Plaid OpenAPI artifact license were not verified. Specific permissive SDK/code licenses above were read separately. No license exception or relicensing grant was requested.
- **Cross-platform and forever:** native Windows behavior, backups/recovery, cross-provider identity reconciliation, long-term provider data-retention permissions, settlement recovery and event replay need implementation-specific verification. No existing product's defaults were shown to meet all of them.

This report recommends reuse boundaries only; it does not change the binding decisions or authorize signups, credentials, deployments or money movement.
