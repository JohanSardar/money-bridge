# Money Bridge: assemble existing financial tools first

**Research date: 2026-10-17. Audience: the Money Bridge design/build agent.** This report answers the assembly question under [DECISIONS.md](../design/DECISIONS.md), particularly the build-as-little-as-possible rule. It supersedes the earlier recommendation to make a tracking application the mandatory core; it does not change the binding decisions.

**Method and evidence limits.** Every external URL below was checked on **2026-10-17**, unless explicitly identified as evidence carried forward from the other research files, also dated 2026-10-17. Publication, protocol, release and commit dates are given where established; otherwise the date is retrieval, not publication. Primary evidence means provider documentation, provider-owned packages/repositories, upstream source, licenses and release records. “Documented” is not a live integration test. **Unverified** means not established by the public evidence or dependent on account eligibility, commercial access, client approval or interoperability. **NF** means no official product was found in the bounded search of the provider's public documentation and repositories, not proof that none exists privately. No signups, credentials, account connections or transactions were used. Public repositories were cloned under `/tmp/finance-assembly/` and inspected, never run. An unauthenticated GitHub metadata request returned `403: rate limit exceeded`; source snapshots and public release pages supplied the health evidence instead.

Prior work skimmed: [existing-tools.md](existing-tools.md), [provider-routes.md](provider-routes.md), and [existing-agent-finance-layers.md](existing-agent-finance-layers.md). The parallel [approval.md](approval.md) became available while this report was being written; its findings are reconciled in §4. It confirms that no general approval product is qualified under all current decisions.

## Decision

**Assemble the official provider tools behind a local gateway. Reuse a database and ingestion runtime for the local copy. Do not fork a budgeting application, build an MCP gateway, reimplement provider SDKs, or build passkey approval.** The smallest credible starting assembly is:

| Part | Recommended existing piece | What Money Bridge still supplies |
|---|---|---|
| Provider access | Official Link, Alpaca, Privacy, Kraken, Coinbase, Mercury, Stripe, Brex and Ramp MCPs/CLIs where applicable; official SimpleFIN/Teller/Plaid APIs for bank aggregation | Configuration, capability inventory, narrow adapters where no suitable tool exists, incremental archival ingestion |
| One MCP entrance and tool policy | **agentgateway**, Apache-2.0, standalone deployment | Pinned configuration; one identity/key per agent; explicit allowlists; typed action boundary in front of mutators |
| Local copy | **SQLite**, using **dlt → SQLAlchemy → SQLite** for suitable ingestion; original documents in local content-addressed files | Small provider mappings and durable observation/change records; no budgets, tracking UI or advice |
| Money execution | Original official tool/API, invoked unchanged by a privileged executor | Freeze the intended call, request an existing approval, reconcile the result, enforce idempotency |
| Approval | Provider-native approval where it actually meets the requirement; otherwise an **existing approval service selected by the approval research** | An integration adapter, never a new WebAuthn ceremony or phone approval application |
| Audit and events | Gateway access/OTel logs plus SQLite action/change journal; standard SSE transport | Correlation, redaction, durable receipts, replay cursors and event filtering |
| CLI / API | Existing MCP CLI client initially; small HTTP service/OpenAPI for local records and action requests | Thin product-specific command aliases and typed endpoints, all using the same authorization path |

**Qualification:** no researched gateway was verified to provide all of aggregation, per-agent tool permissions, durable complete audit, and fresh owner-passkey approval of the exact financial instruction out of the box. The read assembly can proceed independently. Unsupported money actions must remain unavailable until a reused approval component is qualified. This is a real unresolved assembly gap, not a reason to implement our own passkeys.

The recommendations are design judgments from the evidence below. In particular, dlt is an ingestion engine, not a complete universal financial connector, and agentgateway's observability is not by itself a forever, fail-closed financial audit journal.

## 1. Official provider inventory

### How to read the inventory

**M / C / A** = official MCP / official CLI / official API. **L** = actual MCP implementation can run locally, normally stdio. **R** = provider-hosted remote MCP. **S** = a local stdio shim that still calls the hosted MCP. A locally running CLI or SDK always still calls the provider's hosted financial system. “Self-hosted Money Bridge” means its storage and orchestration run locally; it does not mean hosting a bank or aggregator.

The inventory covers **every named provider**, the three main US credit bureaus, Zelle, and a few adjacent rails. It is not an inventory of every US bank or credit union. Broad institution coverage comes from aggregator institution/product discovery, and remains account-specific. An official API for an enterprise partner is not necessarily a self-service API for an individual cardholder.

## 2. MCP gateways: what already exists

### The five controls are different

1. **Aggregation:** many upstream servers appear under one client endpoint.
2. **Authentication:** agent identity/key is established and can be revoked separately.
3. **Authorization:** both discovery and invocation are restricted. Hiding a tool in `tools/list`, choosing a URL filter, or setting a prompt is insufficient if the caller can still invoke it directly.
4. **Approval:** a selected call waits for an independent human decision. OAuth consent, a server-installation approval, an audit field named `requires_review`, and a model's confirmation message are not per-call approval.
5. **Audit:** identity/tool/decision/intent/result are recorded durably. Debug logs, sampled traces and metrics are useful but do not automatically establish a complete permanent execution record.

MCP **elicitation** is a way to request form input or send a user to an external URL. A gateway can forward it without implementing a human approval service. It does not by itself prove passkey use, exact-argument binding, one-time consumption, or that the downstream client presents the request to a human. Treat an agent-returned `accept` as untrusted for financial authorization. Version **2026-07-28** also changes the request/interaction contract; an older bidirectional-proxy implementation is not automatically compatible with that revision. [Normative elicitation specification, 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/client/elicitation.mdx).

### Why agentgateway wins this particular comparison

It supplies the hard-to-justify custom infrastructure in a single maintained permissively licensed runtime: heterogeneous upstreams, federation, identity, exact tool-call authorization, OpenAPI adaptation and observability. The inspected authorization example explicitly checks both tool listing and direct invocation. Its release workflow addresses the cross-platform requirement better than an AKS-only architecture. This is a **fit judgment**, not a benchmark or audit result. [Federation example](https://github.com/agentgateway/agentgateway/tree/main/examples/mcp-multiplex), [OpenAPI example](https://github.com/agentgateway/agentgateway/tree/main/examples/mcp-openapi), [release targets](https://github.com/agentgateway/agentgateway/blob/955d56fae09b45f3cb8e85e797dbb1eb06134f77/.github/workflows/release.yml).

Use API-key records with a stable **agent ID in metadata**, strict validation, and a small explicit policy. Never authorize by a caller-supplied `agent_id` HTTP header or by comparing/displaying the secret key in logs. The inspected key implementation supports hashing/redaction and makes the **Optional default** explicit. [Pinned API-key implementation](https://github.com/agentgateway/agentgateway/blob/955d56fae09b45f3cb8e85e797dbb1eb06134f77/crates/agentgateway/src/http/apikey.rs).

**ContextForge is the runner-up**, and may be preferable if built-in token administration, persisted gateway audit and REST/RPC operations save more effort than its additional control plane costs. It can run locally with SQLite; choosing it does not require Kubernetes. But `tools.execute` is an operation permission, not magically “this agent may refund only this charge.” Scoped virtual servers/visibility or a policy plugin remain necessary. Its audit implementation also catches DB logging failures, so a successful request is not proof that audit persistence succeeded. [Token schema](https://github.com/IBM/mcp-context-forge/blob/86af292eeea89c155b437758b52e3b4b83fb9702/mcpgateway/schemas.py), [audit implementation](https://github.com/IBM/mcp-context-forge/blob/86af292eeea89c155b437758b52e3b4b83fb9702/mcpgateway/services/audit_trail_service.py).

**Do not stack several gateways by default.** Docker isolation can be an execution backend without also becoming a second policy gateway. 1MCP or a generic MCP CLI can be a client without becoming another authorization authority. Pomerium is optional perimeter infrastructure, not mandatory for a loopback-only installation.

## 3. Reuse the data layer, without adopting a tracking product

### Should the local copy itself be an existing application?

**Use an existing persistence/ingestion engine; do not make an existing budgeting application's mutable ledger the universal archive.** The full requirement is wider than transactions: every observed revision, pending→posted identity, deleted/corrected records, provider payloads, documents, holdings and orders, approval/execution states and replayable events. None of the evaluated apps was verified to satisfy that whole contract unchanged.

The reuse rule still applies: a database, loader, protocol parser, provider client and API framework are existing pieces. A small schema/mapping layer for a contract no existing project provides is legitimate glue. Rebuilding aggregation, bookkeeping, charts, budgeting, a SQL engine or a workflow platform is not.

### Freshness and forever history

**Webhooks report upstream availability; they do not make an institution update instantly.** Plaid's normal update webhook says new data is available to fetch; consume the supported cursor/change API and retain added/modified/removed records. Teller notifies on supported refresh/enrollment events; it is not a guaranteed bank-native event per card authorization. SimpleFIN remains a roughly daily backup, with published quotas. Neither buying another MCP server nor running an ETL job every second changes those upstream limits. [Plaid update behavior](https://plaid.com/docs/transactions/webhooks/), [Teller webhook contract](https://teller.io/docs/api/webhooks), [SimpleFIN limits](https://beta-bridge.simplefin.org/info/developers).

For providers with true streams, use the official stream client behind the ingestion worker: e.g. broker order/account events and exchange private WebSockets. These are separate from market-price streams, and **MCP Streamable HTTP/SSE is not automatically a financial event feed**. Link consumer financial-data webhooks and a refresh SLA were not established, so use supported bounded polling and expose observed freshness honestly.

A local install receiving a webhook needs a **reachable HTTPS ingress**. A stable endpoint through an existing network/tunnel component may work, but remote TLS termination, payload storage or relay logs can conflict with “data only on the owner's machine.” Do not assume a tunnel or broker makes that issue disappear. If no acceptable ingress exists, use official polling and report its limit. Gateway/ETL vendor cloud telemetry should not receive financial payloads.

The archive should preserve an append-only **observation envelope**: provider, connection/account, source record ID, fetch/observation time, provider effective/update time if supplied, schema version, payload digest and payload/document reference. Preserve corrected/deleted states as revisions/tombstones. Exclude authentication material, PAN/CVV and one-time payment credentials. A compact typed view can standardize accounts, transactions, balances, holdings, liabilities, documents and action states without implementing tracking logic.

For multi-feed overlap, retain original provenance and account mappings. Do not merge a SimpleFIN and Plaid transaction permanently just because date/amount/merchant happen to match; two legitimate identical purchases exist, and pending/posting IDs change. Maintain reversible match assertions and uncertainty. Old statement/CSV imports extend history; retention “forever” begins with data actually obtained, not records a provider never supplies.

Use existing dlt append/merge/SCD2 primitives where their semantics fit, but do not assume SCD2 alone captures a provider record that was removed between polls. Keep the input/change archive independently recoverable. SQLite's SQLAlchemy destination can create **one file per dataset**; explicitly choose the layout (for example `main`) if the assembly promises a single file. Do not rely on SQLite floating-point numeric affinity for money: preserve provider decimals as strings or explicit integer units plus scale. [dlt merge/SCD2](https://dlthub.com/docs/general-usage/merge-loading), [SQLite destination layout/type caveats](https://dlthub.com/docs/dlt-ecosystem/destinations/sqlalchemy).

This is a proposed composition, not a deployed or tested system. Official provider **read** tools can be federated directly only where that read access is within the agent's scope and the chosen audit guarantee is met. Archival ingestion still has to call them; proxying an MCP response does not persist all provider data.

**“As-is” means preserve the provider's implementation, not grant its entire authority directly to every agent.** For example, the isolated executor can invoke the original Alpaca CLI with the frozen, approved arguments. It must not expose a generic shell where the agent substitutes a new order. For Stripe, a generic `stripe_api_write` call must be reduced to the approved concrete endpoint/payload; a tool name alone cannot express that distinction. For read tools returning both allowed and disallowed accounts, either use appropriately narrowed upstream grants or the typed data service's filtering.

Do not expose management tools that let an ordinary agent register a new server, change tool policies, issue keys, read credential-returning tools, or spawn arbitrary commands. Otherwise it can route around the intended boundary. This is a consequence of assembly permissions, not a proposal to build a second custom authorization engine.

### Approval: explicit unresolved dependency

The bound requirement is **owner passkey confirmation for each money movement**. The assembly must not silently replace this with chat confirmation, a provider login, a company approval role, a remembered OAuth grant, an amount cap or an “allow always” setting.

**Provider-native routes are promising but require qualification:** Link supports phone/passkey approval yet also documents skipping approval below configured limits; Mercury requires its own approval for MCP payment/transfer requests but the reviewed docs do not establish a fresh owner passkey for each exact instruction. Broker/API credentials generally execute directly. A Privacy virtual card created once can be charged later; card issuance approval alone does not establish approval of every future debit.

**Reconciled approval-research outcome:** qualify **Cosignet** first if considering a general reused service. It documents payload-bound WebAuthn approval, API-key REST/MCP, notifications, outbound long-polling and returned assertion evidence. However, it is early access and stores the action payload/assertion in its cloud. It is therefore **not an approved default under the current local-only data decision**. Credential enrollment/export, independent evidence validation and recovery also need qualification. Use private requests, not its optional permanent public reveal. [Provider docs](https://cosignet.com/docs), [data handling](https://cosignet.com/security), [verification](https://cosignet.com/verify), [full local assessment](approval.md).

**Reject the inspected ClawGate public snapshot.** The approval research found that its approval route parses `passkeyResponse` and marks the request approved without verifying that assertion. This assembly investigation independently read the same route and confirmed that missing verification in the handler; separate passkey-login endpoints do not repair the approval path. This is a static source finding, not a live exploit or a claim about the hosted deployment. Do not fork/repair an approval product as the fallback. [Public approval handler](https://raw.githubusercontent.com/AsteyaTech-com/clawgate-api/main/src/routes/approval.ts), [separate authentication handler](https://raw.githubusercontent.com/AsteyaTech-com/clawgate-api/main/src/routes/passkey.ts), [reproducible source hashes and full assessment](approval.md#clawgate-concrete-source-level-rejection).

General approval gateways such as [PermitRail](https://github.com/chokonaira/permitrail) and [ActionProxy](https://github.com/ActionProxy/actionproxy) remain upstream leads, not verified replacements for the passkey requirement. Auth0 CIBA/RAR and privacyIDEA supply useful existing infrastructure, but the approval report identifies fresh-passkey and deployment/semantics gaps. None is silently selected here.

The only glue Money Bridge should write in this area is an adapter to the chosen **existing** approval API and an executor that refuses unapproved calls. If no existing component qualifies, report the limitation and keep those actions disabled. Implementing our own challenge/verification/mobile approval application would violate the reuse decision.

These are **engineering estimates**, not measured code counts, bids or promises. They assume one experienced engineer, a small initial provider set, reused gateway/loader/SDKs, and a qualified existing approval service. Account approval delays and auditing are excluded.

|---|---:|---:|---|

Expect approximately **3,400–8,200 lines of glue/configuration**, plus meaningful fixtures, integration checks and documentation. Rows overlap; estimates should not be added as a precise schedule. A read-first assembly is roughly **3–5 engineer-weeks**; qualifying and adding the first safe actions is another **3–6 weeks**. Complete named-provider parity, every document format and every financial action is **not** in that initial estimate. Each additional official MCP often needs only configuration for live access, but archival fidelity and action semantics still need integration work.

### Smallest build sequence consistent with the decisions

1. **Read-only assembly:** one local agentgateway endpoint, per-agent read keys, SimpleFIN archival ingestion, Link-origin reads if eligible, SQLite typed queries, durable read audit, file import, and freshness/connection status. No tracking UI. Leave unsupported providers explicit in capabilities.
2. **Fresher coverage:** choose **one** of Teller or Plaid based on the user's admitted products; add webhook/stream handling and reconciliation. Use the official Plaid CLI for onboarding/queries where suitable. Add durable event replay before promising live financial events.
3. **One qualified action path:** reuse a provider-native flow or selected existing approval service and connect the original official tool. Start with a narrow action rather than arbitrary API dispatch. Acceptance must include refusal after argument changes, expired/duplicate approval, audit failure and ambiguous provider outcome; this verifies glue without rebuilding approval.
4. **Expand by actual accounts:** official Privacy, Alpaca/Kraken/Coinbase or Mercury/Stripe/Ramp/Brex interfaces as needed. Do not pre-build dozens of wrappers. Consumer Venmo/X/Zelle and bureau gaps remain honestly unavailable/read-only unless an official entitled route is established.

This preserves the assembly priority while identifying the actual irreducible work: **persistent cross-provider observations and mappings, one trusted call path across all doors, approval-to-execution binding, and durable audit/events.** None requires Money Bridge to become a tracking app or a new financial API platform.

## 5. Specific qualifications still needed before implementation claims

- **Gateway release parity:** pin a released agentgateway build containing strict key auth, required policy fields, target platforms and the elicitation paths actually needed. The HEAD evidence does not establish every feature is in the latest release. Test provider OAuth/DCR/refresh through this gateway, especially **Coinbase client allowlisting** and **Ramp redirect allowlisting**.
- **Approval selection:** follow [approval.md](approval.md)'s qualification contract; Cosignet is a research candidate with an explicit cloud-storage conflict, and the inspected ClawGate path is rejected. Qualify exact action, owner passkey, single use, expiry, replay and a local-data-compatible deployment. Do not call a generic gateway approval checkbox sufficient.
- **Provider eligibility:** verify each install can bring its own app/client credentials. Plaid Production/Trial, Teller payments beta, MX commercial access, Link external-data registration and bureau contracts are not solved by an MIT installer.
- **Accounting precision and archive retention:** exercise corrections, removed pending records, provider re-link IDs, duplicate imports and overlapping feeds; verify SQLite/dlt decimal storage and checkpoint recovery. Preserve raw evidence even when the latest projection changes.
- **Audit coverage across doors:** prove direct MCP, HTTP, CLI aliases, provider-native passthrough reads, denied calls and executor calls all correlate to the correct agent. Logs must omit tokens, auth URLs containing secrets, PAN/CVV and payment credentials. Pin retention; default vendor cleanup policies are not “forever.”
- **Freshness and ingress:** measure actual refresh behavior for admitted accounts. Document which events are bank-observed versus app-observed and provide a polling fallback for an install that cannot receive private webhooks safely.
- **License/packaging review:** preserve permissive notices and validate any separately bundled AGPL/MPL/ELv2 component. In particular, MCPJungle is MPL-2.0, Airbyte finance connectors inspected here are ELv2, and Kong's relevant MCP plugin is commercial.

These are bounded validation tasks for a later implementation/pilot. **No account-specific behavior, live gateway interoperability, payment approval, trade execution or end-to-end latency was tested by this research.**
