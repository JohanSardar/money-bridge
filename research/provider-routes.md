# Provider routes for a self-hosted finance connector for agents

**As of 2026-10-17. Research only.** Read `../design/DECISIONS.md` and `existing-tools.md` before this report. This extends the earlier assessment with institution coverage, consumer action surfaces, agent-specific terms, and approval technology. It does not select a budgeting application or change the binding decision to build a reusable connector that anyone can install.

**Evidence convention:** Every external URL below was retrieved on **2026-10-17**. Publication/effective dates are stated where established. “Documented” means a primary source describes the capability; it does not mean a transaction, login, or integration was tested. **Unverified** means public evidence did not establish the claim, or eligibility requires an authenticated account/commercial approval. No signups, credentials, authenticated financial data, or payment operations were used. Public institution-directory queries were performed. Negative search results mean “not found in that directory today,” not permanent non-support. Terms summaries describe published text, not a legal determination of enforceability.

## Findings that change the route assessment

1. **Link now has a consumer agent API, separate from Stripe's merchant API.** Link Agent Wallet, official Link CLI/MCP, and TypeScript/Go SDKs support consumer-authorized purchases and financial-data reads. This is materially more useful than a merchant Stripe MCP for this project. Access and approval details are in section 7. [Stripe developer overview](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet).
2. **Chase is explicitly listed with Teller's `payments` product in the live public institution API.** This closes the earlier evidence gap about institution-level advertising; actual checking-account payment eligibility still requires discovery after enrollment. [Unauthenticated institution catalog](https://api.teller.io/institutions), [catalog contract](https://teller.io/docs/api/institutions).
3. **Venmo's current documentation supports desktop personal P2P and both standard/instant cash-out.** Do not design around the outdated assumption that all Venmo actions require its mobile app. Some controls still do. [P2P instructions](https://help.venmo.com/cs/articles/sending-requesting-money-vhel171), [desktop cash-out instructions](https://help.venmo.com/cs/articles/how-to-transfer-money-to-a-bank-account-vhel293).
4. **X Money is a real, rolling-out U.S. product with a web surface and published agentic-use terms.** Its public documentation also explicitly says to find “X Money” in Plaid. Public documentation for an independently usable X Money action API was not located. [Product](https://money.x.com/en), [FAQ](https://money.x.com/en/i/faq), [X Payments terms](https://money.x.com/en/terms-and-conditions).
5. **A local passkey gate can bind approval to an exact instruction, but does not itself restrict an upstream bank session.** The executor holding bank credentials must enforce that binding. Merchant agent-payment protocols supply narrower sanctioned purchase paths; they do not confer universal bank account control. See sections 8–9.

### Teller payments beta: what is actually established

The current [payments contract](https://teller.io/docs/api/account/payments) supports **Zelle only**, originating from checking accounts. Inspect account `links.payments`, then `OPTIONS /accounts/:id/payments`; a catalog flag alone is insufficient. The API creates payees by phone/email and sends payments. Both operations can return a `connect_token` for a human MFA flow in Teller Connect. Payment creation supports `Idempotency-Key`, retained for **72 hours**. Its payment-list endpoint lists payments initiated **through Teller**, not the entire bank's Zelle history.

Besides Chase/Chase Connect, the inspected catalog flags Bank of America, Wells Fargo, and CapitalOne for payments; Amex, US Bank, and PNC entries inspected did not have that flag. Discover capability dynamically rather than hard-code this sample. **Unverified:** beta admission, production commercial terms, fees, per-user limits, Chase account-specific activation, and the institution's authorization of any particular third-party use. Teller supplies neither a documented general card-bill-pay endpoint nor card freezes, disputes, subscription cancellation, or virtual-card issuance in this contract.

## 2. American Express — U.S. consumer cards

### READ

- **Routine feed:** Bridge listing and Teller `amex` support are established above. Plaid has an official OAuth route. Amex is among institutions requiring periodic Plaid consent refresh, normally **12 months**, so an install needs an owner reauthorization path. [Plaid OAuth guide](https://plaid.com/docs/link/oauth/).
- **Backfill/export:** Amex says two years of transaction activity can be sorted/downloaded as **PDF, Excel, or CSV**. A separate FAQ limits its accounting-software export experience to recent activity plus **six billing statements**, including Quicken/QuickBooks. Treat these as different surfaces; test which is offered rather than promise two years of every format. The U.S. online-account page advertises **up to seven years of billing statements**; archived statements can take **24 hours** to appear. Specific raw OFX/QFX file extensions and a currently working direct OFX server were **not verified**. [History FAQ](https://www.americanexpress.com/us/customer-service/faq.transaction-billing-statements-history.html), [software export FAQ](https://www.americanexpress.com/us/customer-service/faq.download-export-transactions-software.html), [online account features](https://www.americanexpress.com/us/customer-service/digital/create-an-online-account.html).
- **Official consumer API:** No public self-serve API for an arbitrary cardholder to retrieve their complete account was verified. The sanctioned aggregator OAuth connection is distinct from issuing the consumer their own Amex developer token.
- **Near-real-time evidence:** Amex documents purchase/account alerts, email/text spending thresholds, and real-time app alerts. These can seed provisional events, not a complete ledger. **Unverified:** exact sender/header/body template, complete amount/merchant/card fields in each alert type, delivery SLA, duplicate behavior, and reversal coverage. [Alert configuration examples](https://www.americanexpress.com/us/explore/additional-card-member-guide.html), [online/mobile alert features](https://www.americanexpress.com/us/customer-service/digital/create-an-online-account.html).

## 9. Passkey approval of the exact action

### Existing building blocks and patterns

**WebAuthn can bind a challenge to an immutable action.** The authenticator signs authenticator data plus the hash of `clientDataJSON`, which includes challenge and origin; it does not sign an arbitrary bank transaction directly. A challenge containing an action digest can therefore provide local evidence of approval when correctly verified. Ordinary WebAuthn UI authenticates the relying party/user; it does not reliably display the payee and amount in trusted authenticator UI. [WebAuthn Level 3 Recommendation, 2026-08-25](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/), [SimpleWebAuthn custom challenge support, 14.0.x docs](https://simplewebauthn.dev/docs/advanced/server/custom-challenges).

| Existing pattern/product | Evidence and reuse value | Limit |
|---|---|---|
| **Secure Payment Confirmation (SPC)** | Browser-mediated payment confirmation binds displayed payment details into signed evidence. Latest inspected W3C publication is a **Candidate Recommendation Draft, 2026-10-13**. [Dated specification](https://www.w3.org/TR/2026/CRD-secure-payment-confirmation-20261013/), [W3C dynamic-linking explanation](https://www.w3.org/TR/htr/) | Payment-oriented browser/issuer/credential integration; not a generic browser extension that adds bank-recognized signatures to Chase/Zelle actions. Cross-browser/deployment coverage requires testing. |
| **SimpleWebAuthn SPC verification** | Upstream explicitly supports verification of SPC responses via a custom expected type. [Guide](https://simplewebauthn.dev/docs/advanced/server/secure-payment-confirmation) | Response verification alone does not implement trusted UI, credential enrollment, transaction binding or payment execution. |
| **ClawGate API** | OSS self-hostable server: agent API keys, passkey approval, short-lived JWT authorization, Docker deployment. [Upstream README](https://raw.githubusercontent.com/AsteyaTech-com/clawgate-api/main/README.md) | Useful reference, small project. **Unverified:** independent audit, exact-action hash binding, single-use execution enforcement, and protection from a privileged agent. Do not adopt its approval token as financial authorization without source review. |
| **iProov HAPS** | Human Approval and Presence Specification includes action-bound consent evidence and assurance/threat-model distinctions. [Upstream](https://github.com/iProov/HAPS) | Explicitly experimental/not production-ready; a specification and models, not a bank connector. |
| **Turnkey activity approvals** | Activity fingerprint approval and WebAuthn-based request-authentication patterns; useful example of approving a specific operation. [Approve activity](https://docs.turnkey.com/api-reference/activities/approve-activity), [stamps](https://docs.turnkey.com/api-reference/overview/stamps) | Primarily wallet/key infrastructure. Hosted service is not a self-hosted consumer-bank control plane. |
| **AP2 / Mastercard Verifiable Intent** | Cryptographically linked purchase mandates and delegation constraints, above | Useful interoperable evidence; exact owner passkey policy still belongs in the trusted approval component. |

Self-hosted server libraries include **`@simplewebauthn/server` + browser**, **`go-webauthn/webauthn`**, and **Yubico `python-fido2`**. They supply WebAuthn ceremonies/verification, not the action queue/executor. Prefer a maintained library and supported runtime over custom verification cryptography. Go's project explicitly remains version 0 and warns of possible breaking changes. [SimpleWebAuthn](https://github.com/MasterKale/SimpleWebAuthn), [Go WebAuthn](https://github.com/go-webauthn/webauthn), [Yubico Python FIDO2](https://github.com/Yubico/python-fido2).

### Recommended approval contract — design inference, not provider behavior

1. Construct a versioned canonical intent containing owner, provider, action, exact source account, normalized destination identifier, integer minor-unit amount/currency, maximum fee, execution date, intent ID and provider idempotency key. Include the full destination behind any friendly label.
2. Freeze it; create a random, short-lived, one-time challenge bound to its digest, e.g. `SHA-256(domain_separator || canonical_intent || random_nonce || expiry)`. **A bare deterministic action hash is insufficient** for replay/freshness control. Keep the nonce/server state and expected digest outside agent control.
3. Show the exact action on a trusted owner confirmation origin. Require a fresh WebAuthn assertion with user verification, correct owner credential, RP ID, origin, challenge and expiry. Verify the complete WebAuthn response, not just its signature or a “user logged in” flag. For remote phones, use a stable HTTPS relying-party origin; a random changing tunnel hostname changes the credential relationship.
4. Atomically consume the approval and submit only the frozen intent through an isolated executor. Any destination, amount, fee-limit, source or date change requires new approval. Treat ambiguous submission as an unknown state to reconcile, not permission to submit again.
5. Preserve the intent, assertion, approval decision, provider request/reference and result locally; separately reconcile settlement. Provider MFA remains required when requested, even after local approval.

**Critical trust boundary:** If the reasoning agent has root access, a raw Teller payment token, Link spend authority, or an unrestricted signed-in bank browser, it can bypass a merely advisory local gate. Put credentials and final submit behind a process/OS boundary that only accepts consumed approvals. Passkeys must remain owner-controlled; synchronized passkeys are not necessarily device-bound hardware keys. A passkey unlock can use a device PIN, so “requires passkey” is not the same as “requires biometrics.” These are architectural consequences of the standard and the project's threat model, not features any provider promised.

Bank AutoPay and recurring transfers listed above are available provider features, but approving their setup once does **not** satisfy the current requirement to confirm **every money movement** with the owner's passkey. Using standing authorization would require a separate product decision; it is not an implied exception.
