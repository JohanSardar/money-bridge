I compared all 601 lines of [Astra's design](../astra/DESIGN-astra.md) (**A**) with all 188 lines of [Claude's design](../claude/DESIGN-claude.md) (**C**), then applied [Claude's round-one revisions](claude-r1.md). ## 1. D1–D7

**D1 — Agree on SQLCipher and encrypted blobs; disagree with making volume encryption optional.** Claude's concession resolves database/blob encryption. Retain an encrypted data volume, protected keys, encrypted backups, and safe temporary storage. “Keep the FDE check … as an extra warning” must not waive Johan's “disk encrypted” requirement. An inconclusive detector is an installation limitation, not evidence of compliance. SQLCipher documents encrypted database/WAL pages but also requires attention to unencrypted temporary stores. [SQLCipher design](https://www.zetetic.net/sqlcipher/design/).

**D2 — Agree; I withdraw frp as the preferred push profile.** Tailscale explicitly documents a TCP proxy whose relay cannot decrypt the traffic; the Tailscale server **on the owner's device** terminates TLS. Its certificate documentation says certificate and ACME private keys are generated and stored locally. Claude's central claim is correct. [Funnel architecture](https://tailscale.com/kb/1223/funnel), [certificate handling](https://tailscale.com/kb/1153/enabling-https).

Use **polling by default; optional Funnel to a separate restricted webhook receiver; frp as an advanced alternative**. Default HTTPS forwarding terminates TLS in local Tailscale, not necessarily in Money Bridge's receiver; raw `--tcp` forwarding is a distinct mode. ACME is automated, not absent. Funnel requires Tailscale/MagicDNS/HTTPS configuration, uses the tailnet's DNS name and restricted ports, has bandwidth limits, and is currently documented as beta. It exposes a public endpoint; validate provider signatures, bound intake, and never expose Core or executor routes. [Funnel CLI](https://tailscale.com/kb/1311/tailscale-funnel). Drop the ordinary Cloudflare HTTPS tunnel profile: Cloudflare's edge/origin certificate model terminates client HTTPS at its edge. [Cloudflare TLS model](https://developers.cloudflare.com/ssl/concepts/).

**D3 — Agree.** No standing money approvals initially. Every new money instruction needs fresh owner passkey approval. A future mandate requires Johan to change the binding rule; limiting it to own accounts does not create an exception. Local annotations remain approval-free and undoable.

**D4 — Agree with sequencing.** Use a pinned `uv tool install` developer distribution for the initial read-only stages, then signed native packages before a general-public or live-money release on each supported OS. `uv` can download Python automatically; that alone does not establish SQLCipher wheel availability, service identities, secret-store access, or private provider runtimes. [uv Python management](https://docs.astral.sh/uv/concepts/python-versions/). Keep encryption, scopes and audit in the early stages; do not install powerful production credentials into an agent-writable developer environment. Paper rehearsal is a distinct test profile. Native isolation must pass on each OS before that OS enables money actions.

**D5 — Agree.** Separate executor identity is mandatory for live actions, with protected binaries/configuration/journal, authenticated IPC, private upstream children, and tested ACLs. Merely selecting `keyring` does not supply isolation: its macOS documentation permits other scripts using the same Python executable to retrieve its secrets without a new prompt. [keyring security considerations](https://keyring.readthedocs.io/en/latest/#security-considerations).

**D6 — Agree.** Adopt A:397–405: reversible local organization needs scoped permission and undo; cancellations, disputes, beneficiaries, virtual cards and account/security changes are separately qualified high-impact capabilities. They are disabled until qualified and require owner approval when enabled.

**D7 — Agree on the requirement; the proposed usernames are insufficient proof.** `johan` versus `money-bridge-exec` works only if the agent cannot elevate, rewrite service code/policy, access secrets, or control the approval session. Core/archive isolation also matters for scoped reads. Linux tracing checks recognize privileged capabilities as well as user identity. [Linux ptrace access checks](https://man7.org/linux/man-pages/man2/ptrace.2.html). Johan must confirm the actual agent privilege model; do not assume Toy lacks sudo/admin access.

## 2. Material differences omitted from D1–D7

**M1 — Read-adapter placement.** C:102: “Holds every provider credential”; C:103 exposes `sync` through the executor. A:146,356,478 puts genuinely read-only adapters/secrets in Source host; only inseparable money-capable credentials live in the executor. **Prefer A.** Parsing every bank response in the money-credential process unnecessarily expands its trusted code. Restrict reads using powerful credentials there, then normalize in Core.

**M2 — Ownership of action authority.** C:23,91–94 places freezing/approval in Core, then “Core hands `(intent, approval_evidence)`”; C:124 places action tables in the common database. A:150–164,194,330 puts immutable intent, policy, approvals, reservations and attempts in a private executor journal. **Require A's boundary.** If compromised Core can rewrite consumed markers or policy, signature re-verification alone cannot prevent replay or limit bypass. Core may relay proposals/status; the executor must own preparation, approval retrieval and submission. A public-style `execute(intent,evidence)` RPC is unnecessary; submit only executor-owned records.

**M3 — Observation identity and repeated values.** C:55: “idempotent on `(source, object_id, payload_hash)`”; C:116 saves observations only “where the payload changed.” A:203,238 retains fetch observations separately from financial revisions. **Reject C's global hash identity:** A→B→A must create the third revision. Identical later fetches still establish observation time/coverage. Scope identity by connection/account/entity generation; deduplicate content bytes and redelivered provider events, not all historical occurrences of a value.

**M4 — Pending disappearance.** C:60: heuristics are “confirmed when the pending disappears,” and “a vanished pending becomes a `removed` revision.” A:234–236 preserves uncertainty unless explicit removal or a qualified complete snapshot establishes it. **Require A.** A rolling-window omission proves neither posting nor cancellation; an authorization hold can disappear without posting. Plaid supplies explicit removal/addition and optional matching IDs, sometimes on different pages. [Plaid transaction states](https://plaid.com/docs/transactions/transactions-data/). Teller recommends ID reconciliation with a 7–10-day overlap; description similarity is not its identity contract. [Teller transactions](https://teller.io/docs/api/account/transactions).

**M5 — Cross-source merging and precedence.** C:60: one Chase transaction “becomes one `txn` with two `sightings`.” A:202,242–244 requires confirmed account links, evidence-backed transaction relations, primary-source coverage, and explicit unresolved overlaps. **Reject automatic heuristic merging.** Two identical purchases must survive; two transfer legs are distinct facts. Keep provenance and reversible relations; similarity yields `possible_match`, not identity. C does not specify sufficient evidence for its merge.

**M6 — Atomic checkpoints and pagination.** C:60 makes revisions/events atomic, but C:67 mentions a next cursor without specifying its commit boundary. A:248–250 also commits the checkpoint and stages complete logical updates. **Require that stronger contract.** A committed cursor without its rows loses history after a crash. Plaid explicitly requires restarting an interrupted/mutated pagination loop from the original cursor. [Plaid sync contract](https://plaid.com/docs/api/products/transactions/). Atomic outbox agreement alone does not cover this.

**M7 — Backfill stopping rule.** C:71 stops after “nothing for 2 consecutive windows”; A:251–255 records gaps and uses provider-specific continuation/boundaries. **Reject two empty windows as completion evidence.** An account inactive for six months can contain older history. A budgeted pause is acceptable only with explicit incomplete coverage and resumable progress. SimpleFIN's 90-day restriction is a request-window limit, not a universal history boundary or pagination strategy. [SimpleFIN limits](https://beta-bridge.simplefin.org/info/developers). Imported rows also need mapping-version/row provenance and duplicate-safe re-import.

**M8 — Meaning and breadth of the archive.** C:56 offers only `as_of`; C:117–123 lists accounts/transactions/holdings/orders/documents and generic revisions. A:200–218,240 explicitly separates effective time from knowledge time, balance kinds, complete holdings snapshots, securities, bills/due dates, liabilities, recurring-source facts, tax/credit-score metadata and business/personal annotations. **Require these semantic contracts**, without demanding a separate table for every kind. Preserve source precision/signs/date-only values and parser versions; unknown is not zero. This is an omission, not evidence Claude opposes those data kinds. It matters because DECISIONS:12 explicitly requires them.

**M9 — Approval verification and permitted cloud payload.** C:92 sends “canonical action + digest”; C:94 only says “re-verifies the evidence”; C:152 says a compromised Cosignet “can't move money without our Executor.” A:336–352 requires pinned owner credentials, full assertion checks, exact-effect display and minimal approval cards. **Require A's qualification gate.** Cosignet's own hash self-check is explicitly not full WebAuthn verification. Its server stores payloads/assertions; use private links and no public reveal, and keep secrets/history local. A cloud service controlling the approval page can mislead the signer even when signatures verify; “no bank key” is not a complete compromise defense. [Cosignet verification contract](https://cosignet.com/docs), [storage and trust model](https://cosignet.com/security). Missing owner-key export or trustworthy enrollment keeps the affected actions off.

**M10 — Link is not an automatic exception.** C:177 promises purchases “with Link's own approval”; C:183 says “no money actions except Link” if Cosignet fails. A:336,352,364 qualifies native approval too. **Reject the unconditional exception.** Link documents policies permitting requests without manual approval, and approved requests can release payment credentials before a purchase occurs. Keep credentials inside the executor; qualify fresh exact-action passkey enforcement and an official merchant API completion/recovery path. Do not return PAN/CVC/payment tokens or fall back to browser checkout. Failed native qualification requires qualified Cosignet as well, or disables the route. [Official Link CLI](https://github.com/stripe/link-cli).

**M11 — Exactly-once and provider recovery.** C:84 promises “exactly once … or not at all”; C:94 assumes “provider's idempotency key = intent id.” A:383–393 distinguishes local submission control from provider execution. **Reject the universal promise.** Add agent request-key deduplication, durable pre-submit attempts, atomic claims and per-provider duplicate/lookup contracts. Teller retains idempotency behavior for 72 hours; Alpaca uses client order IDs and explicitly warns against resending timed-out orders without confirmation. [Teller payments](https://teller.io/docs/api/account/payments), [Alpaca order handling](https://docs.alpaca.markets/us/docs/working-with-orders). An unknown outcome may remain unresolved; never convert an empty lookup into permission to resend.

**M12 — Financial bounds, lifecycle and limits.** C:87 has `succeeded/failed`; C:98 proposes a “daily outflow cap” and approval for every limit change. A:318–332,383,401–403 freezes currency, destination versions, fees, environment, order terms and expiry; distinguishes acceptance from settlement; reserves gross exposure atomically against rolling per-account/currency ceilings. **Prefer A.** Count unknown attempts/open commitments; distinguish abandoning an unsent intent from cancelling an executed provider order. Initial live trades should be cash long-only limit orders, with other forms separately qualified. Owner-authenticated reductions/revocation should be immediate; increases require the stronger owner path. Johan chooses cap values; Fable should settle policy mechanics and initial trade scope.

**M13 — Scope depth and owner administration.** C:78–79 offers operation scopes plus optional account restrictions; C:109 includes `mb keys create` beside agent commands. A:430–436 additionally separates owner management and supports connection/field/date/raw-document grants. **Require explicit owner-only key/policy/connector administration and uniform authorization across current/history/events/counts/pass-through.** Otherwise key creation or a broad provider read defeats the scopes. Event access must intersect the underlying data grants; revoke active streams promptly. Fine-grained field/date controls are a scope choice for Fable, not already agreed merely because both designs say “scoped keys.”

**M14 — Audit and event delivery contracts.** C:77 records `(principal, operation, resource, outcome)` “before the response leaves”; C:108 promises SSE replay forever. A:440–454 records reproducible released results and audits stream chunks before release, with fail-closed commits, bounded queues, filtered resumable cursors and at-least-once delivery. **Require these failure semantics.** One start-of-stream audit does not account for later disclosures; an unbounded slow subscriber can exhaust memory. Prefer A's backup-anchored audit hash chain as tamper detection, with no claim of administrator-proof immutability. This extends the conceded audit/outbox principle rather than contradicting it.

**M15 — Backup, restore and upgrade safety.** C:128: backup API “plus the `files/` folder”; A:263–265,500 includes blob manifests, both journals, schema/key recovery and read-only restoration. **Require A's recovery contract.** SQLite's backup API snapshots a database, not the application's separate blobs or action authority. [SQLite backup API](https://www.sqlite.org/backup.html). A restored pre-payment journal must never replay the payment. Reconcile and establish a new execution epoch before enabling actions; protect migrations and rollback similarly. Backups need an owner-controlled destination and a tested key-recovery path.

**M16 — Proxy policy beyond hiding money tools.** C:38,103,107 says money tools are hidden and read tools passed through; A:358–360 pins schemas/classifications, captures/redacts reads, and disables unwanted forwarding. **Require A's controls.** FastMCP forwards eligible HTTP headers, including Authorization, to HTTP/SSE backends by default; it also forwards protocol features and does not inspect returned tool payloads. Disable incoming-header forwarding and unneeded sampling/roots/elicitation/logging, validate outputs, and deny unknown tools/direct hidden calls. [FastMCP proxy contract](https://gofastmcp.com/servers/providers/proxy). Namespacing is not an authorization or redaction boundary.

**M17 — Additional egress and ingestion features.** C:108 adds “optional outbound signed webhooks to an agent URL”; C:141 adds provisional bank-email alerts. A:450–454 exposes SSE/pull and leaves interpretation to consuming agents. **Defer outbound callbacks:** SSE/pull meets the requirement without a destination registry, delivery retries and SSRF/disclosure controls. **Accept externally supplied provisional alerts later**, through provenance-bearing imports, with the mailbox connector outside Money Bridge; never treat email as authoritative bank state or authorization. Neither extension is an initial requirement.

**M18 — Distribution and import additions.** C:160 offers Docker; A:498–502 prioritizes native services. **Defer a supported Docker distribution** until storage, unlock and identity isolation are qualified; a container is not a waiver of D5/D7. C:70 explicitly adds `ofxtools` for OFX/QFX; A's initial milestone emphasizes CSV/document archival. **Accept early OFX/QFX via the existing parser** when its fidelity tests pass. C:37's Python 3.12 is an acceptable candidate, not a reason to skip A's release compatibility matrix. These are delivery choices, not reasons to rewrite Python in Go.

**M19 — Enrollment reuse.** C:69,158 embeds a local Plaid Link page; A:511 tries the official CLI/Hosted Link first, then SDK-backed enrollment if needed. **Prefer the existing flow when secure credential handoff and platform support fit.** Plaid's CLI already launches Hosted Link and stores resulting credentials; its documented distribution is Homebrew. [Plaid CLI](https://plaid.com/docs/resources/cli/). Keep those credentials in the service identity's protected storage. The local official widget remains a valid fallback, not a custom bank website automation flow.

**M20 — Release evidence and effort.** C:165–169's scenario list and “after approval works” live pilot omit A:527–553's explicit crash/concurrency/restore/schema-drift cases, independent effect logs, second-owner install, and independent pre-money security review. **Require those acceptance cases**; broaden pure invariant tests beyond matching/digests where useful. Start cross-platform read smoke tests during development rather than deferring platform discovery to C:179's final milestone; release enablement remains per OS. C:47 estimates 4,000–6,500 lines including fakes; A:101–111 estimates 6,200–10,200 production lines excluding tests. **Do not present those as equivalent budgets or cap safety work to either estimate.** Measure the first vertical slice, then re-estimate packaging and recovery.

Two original differences are **already closed by Claude's round-one text**, not new disputes: its adoption of A §6.1 supersedes C:71,134–143's polling/latency claims; its stated milestone agreement supersedes C:176–178's Teller/action sequence. Use SimpleFIN → history → Plaid → Teller → rehearsal → first qualified live action → expansion, with D4's revised packaging timing. No separate dispute over identical framework choices, CLI spelling, or equivalent table layouts.

## 3. Additional wrong or unsafe claims/gaps

- **Source text is not executable trust.** C:107,148's `untrusted_text` marker alone does not prevent prompt injection, terminal escapes or malicious URLs. Apply A:366,462,470: safe rendering, bounded isolated file parsing, fixed executable/argument lists, and SSRF/redirect restrictions for imports, connection URLs and merchant requests. Never execute provider “next command” text.
- **Secret-store names are insufficient.** C:46,158–159 does not specify service-home enrollment, backend validation or unattended unlock. Require A:474–480's role-specific storage, no plaintext/null fallback, private CLI token files, and locked-state behavior. A read-only developer profile must also disclose that a same-user shell can bypass file-based read scopes unless the archive service is isolated.
- **Freshness absolutes must be deleted.** C:141's “adds under a second” is unmeasured and contradicts polling, sleep and outages. C:134's “Up to ~24 h” is not an availability guarantee. C:137's Link rationale cannot cover external bank data: Stripe documents asynchronous Financial Connections refreshes. [Stripe transaction refresh](https://docs.stripe.com/financial-connections/transactions). Claude's adoption of A §6.1 resolves the intended contract; update the conflicting sentences.
- **Verify interface names.** C:70,137 names `read_link_transactions` as the read operation. In current CLI documentation this is an authorization action; the documented fetch command is `link-cli transactions list`. Do not assume the permission label names an executable CLI command or the locked MCP tool; pin and test that manifest. [Link Financial Insights](https://github.com/stripe/link-cli#financial-insights).
- **Enrollment and action examples are conditional.** C:90's Chase→Amex bill payment and C:167's own-account transfer are not established action routes. Teller's cited payments contract currently discovers Zelle support per account; it does not establish generic card-bill payment support. Keep those examples synthetic until a specific official endpoint qualifies. C:175's X Money and C:178's Privacy.com remain candidates, not promised entitlements.
- **Scope the Plaid trial statement.** C:184's ten-connection claim applies to eligible new US/Canada teams: the current plan permits ten Production Items before full Production approval; older teams have different access arrangements. Enrollment still needs actual entitlement checks. [Plaid's current trial explanation](https://support.plaid.com/hc/en-us/articles/16194695660311-Can-I-use-Plaid-for-free).
- **“Complete copy of everything” overpromises.** C:7 should mean every observed financial fact and original import, with gaps disclosed. Neither design can recover unobserved intermediate states. Do not archive live payment credentials under the retention rule. C:166's “Cosignet test tenant” is also a qualification prerequisite, not demonstrated sandbox availability.

## 4. Disposition

**RESOLVED — both positions now agree**

- D1: SQLCipher plus authenticated encrypted blobs and protected keys; volume-encryption wording remains below.
- D2: polling default; optional Funnel to isolated webhook intake; frp alternative; no ordinary Cloudflare HTTPS tunnel for financial bodies.
- D3/D6: fresh approval per money instruction; no initial standing money grants; reversible local organizing with undo; separately qualified high-impact actions.
- D4/D5/D7: developer read-only packaging first, native signed public/live releases, mandatory tested service isolation and no agent authority to bypass it. Actual host privileges need Johan's confirmation.
- Existing shared architecture: Python/FastMCP/FastAPI/Typer, local SQLite evidence/events, official private provider tools, scoped keys/audit, approval before execution, unknown-outcome reconciliation, staged fake/sandbox/owner-approved real testing.
- Round-one revisions: A §6.1 freshness and aggregator/milestone order. M17's externally sourced provisional alerts, M18's reused OFX/QFX parser and compatible Python candidate are accepted within the stated boundaries.

**UNRESOLVED — Fable to adjudicate after Claude's response**

- D1 residual: retain mandatory encrypted-volume handling; Fable may resolve detection/installation behavior, not waive Johan's rule.
- M1–M8: read-host placement, executor authority, evidence identity/matching, atomic ingestion, backfill and data semantics.
- M9–M16: verifiable/minimal approvals, native Link qualification, recovery guarantees, limits/action scope, access/audit/feed contracts, restore safety and proxy controls.
- M17–M20 remaining choices: defer outbound callbacks/Docker, enrollment reuse, release evidence and realistic effort. The specific unsafe omissions in §3 also require correction or an evidence-backed response.
- These are **Astra's positions**, not concessions attributed to Claude. Binding requirements and documented provider contracts are constraints on the tiebreaker, not preferences to vote away.

**FOR JOHAN — owner decisions, not implementation guesses**

- Whether to authorize any future standing mandate; current answer remains **no**. Choose initial accounts, route, caps and acceptable trading scope before a live pilot.
- Confirm agent shell/elevation/browser privileges and the usable encrypted storage/backup/unlock arrangement; otherwise live-action enforcement cannot be claimed.
- Choose whether to enable optional public webhook intake, accept third-party service/signing costs, and authorize paid refresh budgets; polling/read-only operation remains useful meanwhile.
- Review the concrete Cosignet approval card and retention/disclosure behavior during qualification. Round 5 already authorizes its limited action-detail cloud use; no new approval for that existing decision is implied.
